# Issue Expectations Guide — Y1, Y2, Software Engineering 1 and 2

**Last reviewed:** 2026-11-02  
**Purpose:** Explain in practical terms what the existing BD-001–BD-070 assignments and the Software Engineering 1/2 work expect contributors to deliver.

## How to use this guide

This is an explanatory companion, not a replacement for the issue or assignment
itself:

- The [70-task register](./21-70-intern-task-register.md) is the source for BD
  IDs, task titles, team, level, priority, independence, and shared acceptance.
- The [Y1 priority list](./y1-task-priority-list.md) and
  [Y2 priority list](./y2-task-priority-list.md) are the source for each task's
  year level and priority.
- The [intern task allocation](./03-intern-task-allocation.md) is the source
  for Software Engineering 1/2 assignments.
- GitHub is the source for live issue status, assignee, comments, and review
  state. The “open” and “completed” wording below reflects the allocation
  document, not a live check of every GitHub issue.

Each BD task is intended to be independently demonstrable using agreed typed
contracts, local fixtures, and a mock adapter where production integration is
not ready. Keep pages thin, validate inputs, keep tenant context server-side,
and do not treat mock data as persisted production data.

## Shared completion expectations for BD-001–BD-070

Unless the issue lead has approved a different verification approach, a
completed BD issue should include:

1. The behavior or audit described by the issue, demonstrated against its
   intended user role and surface.
2. Tests appropriate to the change. Include rejection and tenant-isolation
   cases wherever authorization or tenant-owned data is involved.
3. Passing repository checks: lint, typecheck, tests, and build. Report the
   exact commands and results in the PR.
4. Updated documentation and evidence such as a short demo, screenshots,
   test output, or audit results.
5. A reviewed PR linked to the BD issue and the required technical-lead
   approval.

P0/P1 describes launch relevance, not a dependency sequence. Follow the
independence and acceptance details in the issue register; do not make a task
wait on a sibling unless a lead explicitly approves a dependency.
