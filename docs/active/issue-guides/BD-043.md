## Implementation sequence

1. Define create/activate/suspend lifecycle with platform-only authorization.
2. Implement guarded tenant updates and block accidental cross-tenant mutations.
3. Record administrative actions with audit metadata and return safe errors.
4. Test suspended tenant behavior and invalid transitions.

## Verification scenarios

- [ ] Non-platform user cannot create or suspend tenants.
- [ ] Suspension follows documented effect on sessions/access and is audited.

## Constraints and dependencies

- Platform functions require elevated server-side guards and audit trails; do not rely on hidden buttons for authorization.
- Use a typed fixture or mock adapter when another team has not yet delivered its backend; do not block all progress on a sibling issue.
- Obtain lead approval for changed API contracts, identity permissions, database migrations, protected customer data, and deployment controls.
- Keep `pnpm` workflow and TypeScript strict conventions; preserve tenant isolation and private/internal visibility.
- This task is not an authorization to introduce a new product feature unrelated to its stated outcome.

## Acceptance and required pull-request evidence

- [ ] Task-specific output is attached or demonstrated: **Tenant lifecycle tests, transition table and platform screenshot**.
- [ ] The verification scenarios above pass; include positive, negative and tenant/role scenarios when relevant.
- [ ] Record commands and actual results for `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build`, or explain legitimate exceptions for a review-only task.
- [ ] Add screenshots, sanitized test logs, migration results, or an audit table sufficient for another student to reproduce the result.
- [ ] Update impacted active documentation and link the individual issue from the PR. No customer data, credentials or `.env` files in submissions.
- [ ] BlazeWebWorks technical lead or an independent designated reviewer approves the change. **No self-approval.**
