## Outcome

Deliver **job card persistence** as a bounded, independently reviewable change or assessment. Expected task-specific evidence: **Job-card migration/service/API tests and persistence demo**. Begin with the code as it exists today; confirm whether a function is already implemented, partially implemented, or mock-backed before adding code.

1. Read [`AGENTS.md`](https://github.com/BlazeWW/BlazeDiagnosis/blob/main/AGENTS.md) and [the test baseline](https://github.com/BlazeWW/BlazeDiagnosis/blob/main/docs/active/18-test-baseline-and-quality-plan.md). Check out current `main` locally, then open the paths above.

## Implementation sequence

1. Trace job-card creation/listing from the station page to server service and database schema.
2. Implement tenant-scoped create/read operations with validated customer and vehicle references.
3. Use server-generated IDs and transaction boundaries for related writes.
4. Replace page-only demo success with reloadable persistent records.

## Verification scenarios

- [ ] Create/reload returns the saved job card on a disposable DB.
- [ ] Invalid vehicle/customer relation and cross-tenant record access are denied.

## Constraints and dependencies

- Agree job status and evidence visibility rules with the engineering lead before altering persistence or customer-facing DTOs.
- Use a typed fixture or mock adapter when another team has not yet delivered its backend; do not block all progress on a sibling issue.
- Obtain lead approval for changed API contracts, identity permissions, database migrations, protected customer data, and deployment controls.
- Keep `pnpm` workflow and TypeScript strict conventions; preserve tenant isolation and private/internal visibility.
- This task is not an authorization to introduce a new product feature unrelated to its stated outcome.
