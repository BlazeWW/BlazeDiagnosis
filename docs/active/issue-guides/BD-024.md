## Outcome

Deliver **mobile item-level approvals** as a bounded, independently reviewable change or assessment. Expected task-specific evidence: **Mobile walkthrough screenshots, interactive tests and adapter contract**. Begin with the code as it exists today; confirm whether a function is already implemented, partially implemented, or mock-backed before adding code.

## First practical session

1. Read [`AGENTS.md`](https://github.com/BlazeWW/BlazeDiagnosis/blob/main/AGENTS.md) and [the test baseline](https://github.com/BlazeWW/BlazeDiagnosis/blob/main/docs/active/18-test-baseline-and-quality-plan.md). Check out current `main` locally, then open the paths above.
2. Record current observed behavior (including failing commands or missing APIs) in the linked GitHub issue. Do not assume a roadmap checkbox proves a working implementation.
3. Create a `feature/BD-024-short-description` branch and start with the smallest test or reproducible evidence for the proposed change.

## Implementation sequence

1. Build a small-screen quote view showing item, cost, choice and total impact clearly.
2. Allow approve/decline per item and a clear review/confirm action using typed mock adapter initially.
3. Preserve selections on retry and handle stale/revised quote responses.
4. Use meaningful button labels, keyboard support and responsive layouts.

## Verification scenarios

- [ ] Each item decision is unambiguous on mobile and can be corrected before submission.
- [ ] Unauthorised or expired quote returns safe error; no fabricated persisted approval.

## Constraints and dependencies

- Do not change financial or approval rules from intuition. Obtain a documented business rule and keep sent versions auditable.
- Use a typed fixture or mock adapter when another team has not yet delivered its backend; do not block all progress on a sibling issue.
- Obtain lead approval for changed API contracts, identity permissions, database migrations, protected customer data, and deployment controls.
- Keep `pnpm` workflow and TypeScript strict conventions; preserve tenant isolation and private/internal visibility.
- This task is not an authorization to introduce a new product feature unrelated to its stated outcome.

## Acceptance and required pull-request evidence

- [ ] Task-specific output is attached or demonstrated: **Mobile walkthrough screenshots, interactive tests and adapter contract**.
- [ ] The verification scenarios above pass; include positive, negative and tenant/role scenarios when relevant.
- [ ] Record commands and actual results for `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build`, or explain legitimate exceptions for a review-only task.
- [ ] Add screenshots, sanitized test logs, migration results, or an audit table sufficient for another student to reproduce the result.
- [ ] Update impacted active documentation and link the individual issue from the PR. No customer data, credentials or `.env` files in submissions.
- [ ] BlazeWebWorks technical lead or an independent designated reviewer approves the change. **No self-approval.**
